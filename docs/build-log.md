# Build Log

A running narration of engineering decisions as they're made — not a changelog of *what* shipped (that's `CHANGELOG.md`), but a record of *why*, written at the time the decision was made rather than reconstructed afterward.

## 2026-07-05 — Repository scaffold

- **License**: Apache-2.0 over MIT. Reasoning: the explicit patent grant is more typical of production-oriented ML tooling, and this project is meant to demonstrate professional engineering practice, not just research code.
- **Compute target**: Colab Pro / notebook-friendly execution, not assumed local GPU. This shapes Module 1 onward — training scripts are written to also work as notebook cells sized to fit a single Colab session, and dataset subsets are chosen small enough to download and train within that constraint.
- **Packaging**: one root `pyproject.toml` with a per-module optional-dependency extra (`cellpainting`, `gnn-scrna`, `genomic-fm`, `dti-gnn`, plus `mlops` and `dev`) rather than either a single monolithic environment or four separate `pyproject.toml` files. The four modules have heavy, occasionally conflicting dependencies (`torch-geometric`, `transformers`, `rdkit`), so installing only the extra needed for the module being worked on avoids dependency churn from unrelated modules, while a single project still gets one shared CI config and one shared `common/` package.
- **Shared code kept minimal**: `common/` holds only the random-seed policy and MLflow logging conventions. Deliberately not a shared data-loading or model-abstraction layer — the four modules are independent problems and forcing a shared abstraction across them (e.g. a generic "Dataset" or "Model" base class) would be premature generalization with no real reuse to justify it yet.
- **Module 1 data plan**: JUMP-CP (Cell Painting Gallery) is ~116TB in full. Starting with the smallest reasonable slice — one plate, a small compound list — to validate the download → CellProfiler-feature → model pipeline end-to-end before deciding whether to scale up to the originally scoped ~30–50 compound / 1–2 plate subset. This is a deliberate two-step approach: validate cheaply, then scale, rather than committing to a larger download before the pipeline is proven to work.
- **CI scope for now**: the CI workflow only installs the `dev` extra and lints/type-checks/tests `common/`, since no module has code yet. It will pick up each module's extra as that module's tests are added, rather than installing all four modules' heavy dependencies (torch-geometric, transformers, rdkit, ESM-2) before any of them are used — that would make every CI run slow for no benefit until there's code to actually test.
- **Minimum Python raised from 3.10 to 3.12**: discovered by actually running `make check` rather than assuming it would pass. `numpy` 2.5's bundled type stubs use a PEP 695 `type` alias statement, which mypy only accepts when its configured target `python_version` is 3.12+; targeting 3.10 made mypy fail on numpy's own stub file, not on project code. Rather than pin numpy to an older release to keep supporting 3.10, raised `requires-python`, `ruff`/`black` target-version, mypy's `python_version`, and the CI Python version to 3.12 together, since the ML dependencies this project pulls in (torch, transformers, PyG) all support 3.12 anyway.

## 2026-07-20 — Built and ran the tabular baseline, with a permutation-based null test

## 2026-07-20 — CNN architecture decision: pretrained EfficientNet-B0/ResNet50, not from-scratch

Made on `module/1-cellpainting-cnn` before writing any CNN code, closing the README's existing placeholder ("Architecture choice ... is not yet finalized and will be recorded in `docs/build-log.md` when decided").

- **Decision: fine-tune a pretrained ImageNet backbone (EfficientNet-B0 primary, ResNet50 as an easy-to-swap fallback) rather than train a custom CNN from scratch.**
- **The binding constraint is data size, not Colab Pro compute.** Both a small custom CNN and EfficientNet-B0/ResNet50 fit comfortably in Colab Pro's GPU memory/time budget, even fine-tuning the full network -- compute doesn't discriminate between the two options here. What does discriminate: under either choice, the CNN's training set is small. Same 14-compound / 4-plate scope as the tabular baseline (see below), at site-level image granularity, gives at most ~504 five-channel image composites (14 wells x 4 plates x 9 sites) -- fewer once a validation split is taken out. Training a randomly-initialized CNN with millions of parameters on a few hundred images is a well-known recipe for either badly overfitting or failing to learn anything generalizable; a pretrained backbone's early-layer features (edge/texture/blob detectors) are comparatively domain-generic and dramatically more sample-efficient to fine-tune, which matters far more here than compute headroom.
- **Verified this holds for Cell Painting specifically, not just generic transfer-learning folklore -- checked the actual literature rather than assuming.** Broad's own DeepProfiler (same team/tool ecosystem this module already relies on for CellProfiler profiles) supports EfficientNet-B0 and ResNet backbones pretrained on ImageNet as first-class, documented options for Cell Painting feature extraction, not a fringe approach. Cell Painting MoA-classification literature reports ImageNet-pretrained CNNs reaching 95-97% accuracy vs. 70-91% training from scratch on a comparable compound/treatment classification task -- a large, consistent gap in the same direction. Recorded honestly rather than cherry-picked: the same literature notes pretraining on same-domain microscopy data (e.g. LINCS) outperforms ImageNet pretraining, which isn't unconditionally better than classical CellProfiler-style features in every large-scale setting either. Same-domain pretraining isn't available to us (would need a large unlabeled Cell Painting corpus and self-supervised pretraining, out of scope) -- ImageNet-pretrained-then-fine-tuned is the best available option given our actual constraints, not a claim that it's optimal in general.
- **First-conv-layer adaptation: expand the pretrained 3-channel stem to accept all 5 channels jointly, not per-channel replication.** Two documented approaches were considered:
  1. **Chosen**: replace the backbone's first conv layer with a new 5-channel `Conv2d`, warm-started (not randomly initialized) by copying the pretrained RGB kernel weights into the first 3 input-channel slots and filling the remaining 2 slots with the mean of those pretrained kernels -- a documented pattern for expanding a pretrained conv stem's channel count without touching the rest of the pretrained network. Keeps later layers seeing one joint embedding of all 5 stains together, consistent with the README's existing "CNN trained directly on raw 5-channel Cell Painting pixel composites" framing, and preserves cross-channel spatial relationships (e.g. relative organelle positioning) that a per-channel approach would throw away until very late in the network.
  2. **Considered, rejected as the primary plan**: DeepProfiler's own documented default for pretrained backbones is different -- a `repeat_channel_crop_generator` that replicates each fluorescent channel to pseudo-RGB (3 copies of the same channel) and runs each channel through the *unmodified* pretrained network separately, concatenating the resulting per-channel embeddings (5 x 1280 = 6400-dim for EfficientNet-B0). Real merits -- zero surgery on pretrained weights, and per-channel embeddings could pair naturally with this module's planned SHAP track -- but the network never sees the 5 stains jointly at the pixel level, contradicts the README's existing framing, and costs ~5x the forward-pass compute per image. Rejected as the primary plan; recorded here as a documented, ready fallback if the joint 5-channel stem underperforms.
- **Data scope: same 14 compounds, same 4 already-verified plates (`BR00116991`-`BR00116994`) as the tabular baseline -- not all 384 wells.** Keeps the CNN and tabular-baseline comparison apples-to-apples on the same label set and scope, and matches the project's established "validate cheaply before scaling" philosophy (see the repository-scaffold entry above): scaling to the full plate's much larger compound platemap is out of scope for this validation pass, same as it was for the tabular baseline. Unlike the tabular baseline's well-level n=56, the CNN trains at image level: 9 sites/well x 14 wells x 4 plates = up to 504 five-channel site composites before any train/validation split. Still small by CNN standards -- that's exactly what motivates the pretrained-backbone decision above, not a case for training from scratch after all. (Site-level composites, not per-cell crops, carried forward from the README's existing wording -- not silently re-decided here; per-cell-crop granularity remains a separate, open question if it's ever revisited.)
- **Not a substitute for the module's cross-batch transfer evaluation.** Training across all 4 confirmed same-batch plates -- likely holding one out for an in-distribution validation split, mirroring the tabular baseline's leave-one-plate-out design; exact split mechanics deferred to when training code is written -- is a within-batch setup, same distinction already recorded for the tabular baseline. Cross-batch transfer still requires a genuinely different batch, not yet selected.

## 2026-07-20 — CNN train/validation split and significance-testing strategy

Made on `module/1-cellpainting-cnn` before writing any training code, closing the deferral in the architecture-decision entry above ("exact split mechanics deferred to when training code is written").

- **Decision: 4-fold leave-one-plate-out, with a rotating internal-validation plate for early stopping -- not a single fixed train/val split.** A CNN needs something the tabular baseline's logistic regression didn't: an internal validation set to monitor during fine-tuning (early stopping, checkpoint selection) that is distinct from the number actually reported as the in-distribution result -- using the same plate for both would leak the "test" signal into the training decision of when to stop. So each fold uses three plate-level roles, not two:

  | Fold | Train (2 plates) | Internal val (1 plate, early stopping only) | Test (1 plate, reported) |
  |---|---|---|---|
  | 1 | `BR00116993`, `BR00116994` | `BR00116992` | `BR00116991` |
  | 2 | `BR00116994`, `BR00116991` | `BR00116993` | `BR00116992` |
  | 3 | `BR00116991`, `BR00116992` | `BR00116994` | `BR00116993` |
  | 4 | `BR00116992`, `BR00116993` | `BR00116991` | `BR00116994` |

  A fixed, deterministic rotation (plate order `91, 92, 93, 94`; test = plate `i`, internal val = plate `i+1 mod 4`, train = the other two) -- not picked to favor any particular fold's result. Every plate serves as test exactly once, internal-val exactly once, and training data in exactly 2 of the 4 folds.
- **All splits are at plate level, never at site/image level within a plate.** Sites from the same well (and wells from the same plate) share physical imaging conditions -- the same exact acquisition run, focus, illumination-correction pass -- so splitting sites from one well across train and internal-val would risk the model partly learning well-specific nuisance signal rather than compound-specific morphology, the same well-known leakage concern that motivated using whole plates (not row-level or image-level folds) for the tabular baseline's LOPO-CV. `configs/data.yaml`'s own build-log entry already documents real inter-plate technical variation within this nominal batch (e.g. the WGA dye-amount difference across plates), reinforcing that plate boundaries are exactly where leakage would otherwise sneak in.
- **Image counts per fold** (9 sites x 14 wells per plate = 126 site composites/plate): **train = 252** (2 plates), **internal val = 126** (1 plate, never contributes to the reported metric), **test = 126** (1 plate, held out entirely for that fold's model). Pooled across all 4 folds' test predictions: **504 out-of-fold predictions total**, covering every one of the 504 site composites in the dataset exactly once -- the reported in-distribution accuracy/macro-F1 is computed by pooling these, the same out-of-fold-pooling design `baseline.py`'s `evaluate()` already uses for the tabular baseline, for methodological consistency between the two tracks.
- **This satisfies the README's existing "In-distribution" definition** (a held-out split from the same imaging batch as training) without any change to that definition -- all 4 plates are the same batch (`2020_11_04_CPJUMP1`). Still explicitly not cross-batch transfer, which needs a genuinely different batch, not yet selected -- same distinction already recorded above and for the tabular baseline.
- **Decision: do not run a full 1000-permutation test like the tabular baseline -- it isn't computationally feasible for a fine-tuned CNN, and a different strategy is used instead.** The tabular baseline's `permutation_test_score` reruns its *entire* CV pipeline once per permutation; that's cheap for a `LogisticRegression` fit (a few seconds) but not for fine-tuning a CNN across 4 folds, where each real run already costs real GPU time. 1000 permutations at that cost would mean roughly 1000x the compute of one real run -- hundreds of GPU-hours -- which doesn't fit the Colab Pro target this module is scoped to. Reusing the tabular baseline's exact recipe unmodified isn't an option; the significance check has to be adapted to what's actually affordable, not silently dropped either. Two adapted checks, both affordable:
  1. **Primary: a closed-form one-sided binomial test of the pooled 504 out-of-fold predictions against chance ~= 1/14, not a rerun-based permutation null.** This reintroduces the "is chance really 1/14" assumption the tabular baseline's permutation test was specifically built to avoid -- except we're no longer assuming it blindly: that permutation test's own empirical null came back at 0.0717 (`null_mean` in `data/raw/cellpainting/baseline/results.json`), which matches the naive 1/14 = 0.0714 rate almost exactly for this specific balanced 14-classes-per-plate design. Reusing that already-measured result to justify a cheap closed-form test for the CNN -- rather than re-deriving a full permutation null via expensive retraining -- is a documented, evidence-based shortcut, not an unexamined assumption. Recorded honestly as a real methodological downgrade from the tabular baseline's test: a binomial test over pooled predictions from 4 different fold-specific models is an approximation (treats the 504 predictions as roughly i.i.d., which they aren't exactly, since each block of 126 comes from one fold's model), not as rigorous as a true permutation null -- an explicit, deliberate tradeoff for compute reasons, not an oversight.
  2. **Secondary: a small number (5) of full label-shuffled retraining sanity runs**, each running the complete 4-fold pipeline on label-permuted data. Not enough shuffles for a real p-value (minimum achievable would be 1/6), and not meant to produce one -- meant as a pipeline-correctness sanity check: if a shuffled-label run also reaches high accuracy, that flags a leakage bug (e.g. a split boundary crossing a plate after all) rather than a real signal, the same kind of sanity check this project has run throughout (e.g. the dry-run file-count checks in `download.py`/`profiles.py`) rather than trusting the pipeline's correctness by construction.
