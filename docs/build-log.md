# Build Log

A running narration of engineering decisions as they're made — not a changelog of *what* shipped (that's `CHANGELOG.md`), but a record of *why*, written at the time the decision was made rather than reconstructed afterward.

## 2026-07-05 — Repository scaffold

- **License**: Apache-2.0 over MIT. Reasoning: the explicit patent grant is more typical of production-oriented ML tooling, and this project is meant to demonstrate professional engineering practice, not just research code.
- **Compute target**: Colab Pro / notebook-friendly execution, not assumed local GPU. This shapes Module 1 onward — training scripts are written to also work as notebook cells sized to fit a single Colab session, and dataset subsets are chosen small enough to download and train within that constraint.
- **Packaging**: one root `pyproject.toml` with a per-module optional-dependency extra (`cellpainting`, `gnn-scrna`, `genomic-fm`, `dti-gnn`, plus `mlops` and `dev`) rather than either a single monolithic environment or four separate `pyproject.toml` files. The four modules have heavy, occasionally conflicting dependencies (`torch-geometric`, `transformers`, `rdkit`), so installing only the extra needed for the module being worked on avoids dependency churn from unrelated modules, while a single project still gets one shared CI config and one shared `common/` package.
- **Shared code kept minimal**: `common/` holds only the random-seed policy and MLflow logging conventions. Deliberately not a shared data-loading or model-abstraction layer — the four modules are independent problems and forcing a shared abstraction across them (e.g. a generic "Dataset" or "Model" base class) would be premature generalization with no real reuse to justify it yet.
- **Module 1 data plan**: JUMP-CP (Cell Painting Gallery) is ~116TB in full. Starting with the smallest reasonable slice — one plate, a small compound list — to validate the download → CellProfiler-feature → model pipeline end-to-end before deciding whether to scale up to the originally scoped ~30–50 compound / 1–2 plate subset. This is a deliberate two-step approach: validate cheaply, then scale, rather than committing to a larger download before the pipeline is proven to work.
- **CI scope for now**: the CI workflow only installs the `dev` extra and lints/type-checks/tests `common/`, since no module has code yet. It will pick up each module's extra as that module's tests are added, rather than installing all four modules' heavy dependencies (torch-geometric, transformers, rdkit, ESM-2) before any of them are used — that would make every CI run slow for no benefit until there's code to actually test.
- **Minimum Python raised from 3.10 to 3.12**: discovered by actually running `make check` rather than assuming it would pass. `numpy` 2.5's bundled type stubs use a PEP 695 `type` alias statement, which mypy only accepts when its configured target `python_version` is 3.12+; targeting 3.10 made mypy fail on numpy's own stub file, not on project code. Rather than pin numpy to an older release to keep supporting 3.10, raised `requires-python`, `ruff`/`black` target-version, mypy's `python_version`, and the CI Python version to 3.12 together, since the ML dependencies this project pulls in (torch, transformers, PyG) all support 3.12 anyway.

## 2026-07-20 — Module 1 download script and real data subset

- **Picked the actual plate/compounds by querying the live bucket, not by reading docs alone**: used `boto3` with an unsigned S3 client against `s3://cellpainting-gallery` directly (no AWS account needed) to list real objects, rather than trusting scraped documentation, which turned out to be incomplete/wrong about file-naming details in places. This confirmed the actual per-well file count (72 = 9 sites × 8 channels × 1 focal plane) and the illumination-correction file count (8) before writing any download logic against them.
- **Plate chosen**: `BR00116991` (batch `2020_11_04_CPJUMP1`), a compound-perturbation plate (not CRISPR/ORF) using the `JUMP-Target-1_compound_platemap`, cross-referenced against `2021_Chandrasekaran_submitted`'s `experiment-metadata.tsv` to confirm perturbation type and rule out picking a genetic-perturbation plate by mistake.
- **Compounds chosen**: the first 14 non-control wells in row A of that platemap (A01, A03–A08, A10–A16) — arbitrary but deterministic (first row, in well order), rather than hand-picking "interesting" compounds, so the selection is reproducible and not subject to unstated curation bias. All 14 are real `trt` (treatment) wells with known Broad compound IDs and gene targets, copied verbatim from `JUMP-Target-1_compound_platemap.tsv` / `JUMP-Target-1_compound_metadata.tsv` into `configs/data.yaml`.
- **8 channels, not the standard 5**: this plate's batch used a WGA-stain variant, so it acquired 3 extra channels (brightfield/autofocus) beyond the standard 5 Cell Painting fluorescent stains. Documented as an open item rather than guessed: the channel-index → stain-name mapping requires reading this plate's own `Images/Index.idx.xml`, which is out of scope for the download script itself (that file's schema isn't confirmed yet) — deferred to whichever step first needs to distinguish channels, i.e. feature extraction.
- **Download script design**: idempotent (skips files that already exist on disk, so an interrupted download can resume), config-driven from `configs/data.yaml` (no plate/well/compound values hardcoded in `download.py`), and supports `--dry-run` to list exact file counts/sizes without transferring anything — used to verify the real numbers above without a 2.4GB download during scaffolding.
- **New `slow` test**: `test_download_plate_subset_dry_run_matches_live_bucket` hits the real bucket (dry-run only) and asserts the 72/8 file counts, so a future JUMP-CP layout change would be caught rather than silently invalidating the download script's assumptions.
- **Did not execute the actual ~2.4GB download in this session**: the script and its dry-run were verified against the live bucket; running the full download is left as an explicit, separate step rather than something done silently as part of scaffolding.
- **CI split on the new `slow` test**: push CI (`ci.yml`) previously had no test marked `slow` yet also had no `-m` filter, so adding a live-network test would have made every push depend on the JUMP-CP bucket being reachable. Fixed `ci.yml` to run `pytest -m "not slow"`, and extended `weekly-smoke.yml` to run the `slow` tests separately (`pytest -m slow`), fulfilling that workflow's own previously-stated intent to "run a tiny real pipeline... once one exists."
- **Ran the actual download**: 1,016 files (1,008 images + 8 illum), 2.45GB, all 14 wells — matched the `--dry-run` estimate exactly. Manifest written to `data/raw/cellpainting/manifest.json` (gitignored; not committed).
- **Confirmed the channel-index → stain mapping, and corrected an earlier guess**: the "8 channels, not the standard 5" bullet above guessed this was because of the plate's WGA anomaly flag. That guess was wrong — cross-referencing three independent sources (this plate's `Images/Index.idx.xml`, the CPJUMP1 batch's own README, and this plate's `load_data.csv`, which all agree exactly) shows ch1-ch5 are the standard 5 Cell Painting fluorescent stains (Mito/AGP/RNA/ER/DNA) and ch6-ch8 are brightfield/z-stack channels this batch collected in addition — unrelated to the WGA flag, which the CPJUMP1 README says refers to dye-amount differences, not a channel-schema change. Recorded the confirmed mapping in `configs/data.yaml` (`channels:`, `model_input_channels: [ch1..ch5]`) and corrected the module README accordingly, rather than silently editing the earlier build-log bullet to hide the wrong guess.
- **Feature-extraction decision, made before writing any extraction code**: checked whether Broad had already published CellProfiler output for this exact plate before deciding whether to run CellProfiler ourselves or write a custom substitute. They had: `workspace/profiles/2020_11_04_CPJUMP1/BR00116991/` contains several pycytominer-processed profile variants, alongside the actual `.cppipe` pipeline file Broad used and a 23.5GB full per-cell SQLite backend. Downloaded and parsed two variants to verify rather than assume: `_augmented.csv.gz` (5,792 real CellProfiler features across Texture/Correlation/Granularity/Intensity/RadialDistribution/AreaShape/Location, all 384 wells) and `_normalized_feature_select_batch.csv.gz` (838 features, pycytominer's per-plate-normalized and redundancy-filtered "ready for downstream ML" variant, also all 384 wells) — both confirmed to include all 14 of our wells.
- **Decision: use Broad's precomputed `_normalized_feature_select_batch.csv.gz` profile, filtered to our 14 wells. Do not run CellProfiler locally; do not write a custom Python feature-extraction substitute.** This redefines what "CellProfiler feature extraction" means for this module going forward: fetching and filtering Broad's already-published profile, not computing features ourselves.
  - Against running CellProfiler locally: headless CellProfiler needs a Java/bioformats dependency plus wxPython, a heavy and fragile install that fits poorly with the agreed Colab Pro compute target, and would require correctly wiring segmentation and per-object measurement modules ourselves to reproduce something Broad has already computed and published for this exact plate.
  - Against a custom substitute (e.g. scikit-image intensity/texture/shape stats): it would only approximate a subset of CellProfiler's categories and wouldn't be numerically comparable to the literature-standard JUMP profiles. With the real thing available as a free, already-verified ~1MB download, a substitute would be strictly worse — more engineering risk for less rigor, not less cost.
  - Scope: this only affects the tabular-baseline / UMAP-SHAP track. The CNN still trains on raw ch1-ch5 pixel composites directly and never runs or consumes CellProfiler output.
  - Corrected `DATA_SOURCES.md`'s earlier claim that these profiles ship as parquet — for this pilot dataset they're gzipped CSV.
  - This decision (and the verification behind it) was written up in `modules/1_cellpainting/README.md`, `DATA_SOURCES.md`, and `configs/data.yaml` before any profile-fetching code was written, matching how the subset size and channel mapping were handled.
- **`profiles.py` written to the same conventions as `download.py`**: config-driven from `configs/data.yaml`'s new `profiles:` section, idempotent (skips re-fetching from S3 if the filtered CSV already exists on disk), `--dry-run` support (always fetches fresh from S3 but writes nothing, for verifying counts). Reuses `download.py`'s `make_s3_client`/`write_manifest` rather than duplicating them.
- **New `slow` tests** in `test_profiles.py`: one confirms the live profile still contains exactly our 14 wells; one confirms the expected metadata columns (`broad_sample`, `pert_iname`, `InChIKey`, `smiles`, `gene`, `pert_type`, `control_type`) are still present; one exercises the real fetch-then-resume path end-to-end (writes to a tmp dir, confirms a second call doesn't re-touch the file). All fast, pure-logic tests (config parsing, row filtering, CSV round-trip) stay unmarked and run in push CI; the live-bucket ones run only in the weekly smoke test, per the existing split.

## 2026-07-20 — Reframed the classification target: compound identity, not MoA

- **No MoA annotation exists for these 14 compounds — checked directly rather than assumed.** `JUMP-Target-1_compound_metadata.tsv` (the source both `configs/data.yaml`'s compound list and the profile `Metadata_*` columns are drawn from) has exactly these columns: `broad_sample, InChIKey, pert_iname, pubchem_cid, gene, pert_type, control_type, smiles`. No `moa` field. The per-compound `targets` gene lists in `configs/data.yaml` are individual gene symbols (e.g. `CACNA1A|CACNA1B|...`), not a curated small set of MoA class labels — grouping 14 compounds into MoA classes from raw gene-target lists would require additional curation work this pilot subset was never scoped to do, and doing it ad hoc would mean silently inventing ground truth.
- **Decision: reframe the classification target from MoA to compound identity — 14-way, `Metadata_broad_sample`/`Metadata_pert_iname`.** This is a correction of what the module was actually measuring, not a scope downgrade: with 14 distinct compounds and no MoA grouping, "MoA classification" was never a well-defined task for this subset. Compound-identity classification is well-defined, uses labels that already exist and are verified in `configs/data.yaml` and the profile metadata, and still supports the module's real question (does a model trained on one imaging context generalize to another). Applies to both the CNN (image input) and the tabular baseline (CellProfiler-feature input) — updated consistently in `modules/1_cellpainting/README.md`, `docs/impact.md`, `DATA_SOURCES.md`, and `src/cellpainting/__init__.py`, not just the baseline that happens to be built first.

## 2026-07-20 — Built and ran the tabular baseline, with a permutation-based null test

- **Built `src/cellpainting/baseline.py`**: pools all four plates' `_normalized_feature_select_batch.csv.gz` profiles (idempotent per-plate local cache, `--refresh` to re-fetch, same conventions as `download.py`/`profiles.py`), runs leave-one-plate-out CV (`sklearn.model_selection.LeaveOneGroupOut`, groups = plate id) with a `StandardScaler` + `LogisticRegression(C=0.1)` pipeline, and assesses significance with `sklearn.model_selection.permutation_test_score` rather than a fixed accuracy threshold. Passing `groups` to `permutation_test_score` shuffles labels *within each plate* (verified by reading sklearn 1.9's `_shuffle` source directly, not assumed from the docstring) — every permutation still has all 14 compounds present exactly once per plate, matching the real balanced design, rather than a global shuffle that could produce degenerate folds. 12 fast tests (config parsing, an in-memory `FakeS3` for the fetch/cache/pool logic, schema-mismatch and wrong-well-count guards, and synthetic informative/uninformative datasets exercising the CV and permutation-test logic itself) plus one live-bucket regression test confirming the real pooled dataset is still 56×838/14-class with a balanced 14-per-plate group structure. Chose logistic regression over a deeper baseline deliberately — it's the "naive/non-deep tabular classifier" the CNN's Evaluation plan section already commits to comparing against.
- **Ran the real baseline**: `python -m cellpainting.baseline --n-permutations 1000` — **accuracy 0.750, macro-F1 0.743** over the 56-sample/14-class LOPO CV, against a permutation null of **0.072 ± 0.036** (matching the 1/14 ≈ 0.071 chance rate almost exactly, a sanity check that the null construction is correct) and **p = 0.000999** (the observed accuracy beat all 1000 permutations — the smallest p-value obtainable at this permutation count, so the real number is likely smaller than reported and re-running with more permutations would only sharpen it, not change the conclusion). Raw output in `data/raw/cellpainting/baseline/results.json` (gitignored). This is a real, reproducible baseline number, not a placeholder — but per `CONTRIBUTING.md`'s documentation convention, it is not yet added to `docs/impact.md`, since that page is reserved for results logged through MLflow, which this run does not yet do.
