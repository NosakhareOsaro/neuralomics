# Build Log

A running narration of engineering decisions as they're made — not a changelog of *what* shipped (that's `CHANGELOG.md`), but a record of *why*, written at the time the decision was made rather than reconstructed afterward.

## 2026-07-05 — Repository scaffold

- **License**: Apache-2.0 over MIT. Reasoning: the explicit patent grant is more typical of production-oriented ML tooling, and this project is meant to demonstrate professional engineering practice, not just research code.
- **Compute target**: Colab Pro / notebook-friendly execution, not assumed local GPU. This shapes Module 1 onward — training scripts are written to also work as notebook cells sized to fit a single Colab session, and dataset subsets are chosen small enough to download and train within that constraint.
- **Packaging**: one root `pyproject.toml` with a per-module optional-dependency extra (`cellpainting`, `gnn-scrna`, `genomic-fm`, `dti-gnn`, plus `mlops` and `dev`) rather than either a single monolithic environment or four separate `pyproject.toml` files. The four modules have heavy, occasionally conflicting dependencies (`torch-geometric`, `transformers`, `rdkit`), so installing only the extra needed for the module being worked on avoids dependency churn from unrelated modules, while a single project still gets one shared CI config and one shared `common/` package.
- **Shared code kept minimal**: `common/` holds only the random-seed policy and MLflow logging conventions. Deliberately not a shared data-loading or model-abstraction layer — the four modules are independent problems and forcing a shared abstraction across them (e.g. a generic "Dataset" or "Model" base class) would be premature generalization with no real reuse to justify it yet.
- **Module 1 data plan**: JUMP-CP (Cell Painting Gallery) is ~116TB in full. Starting with the smallest reasonable slice — one plate, a small compound list — to validate the download → CellProfiler-feature → model pipeline end-to-end before deciding whether to scale up to the originally scoped ~30–50 compound / 1–2 plate subset. This is a deliberate two-step approach: validate cheaply, then scale, rather than committing to a larger download before the pipeline is proven to work.
- **CI scope for now**: the CI workflow only installs the `dev` extra and lints/type-checks/tests `common/`, since no module has code yet. It will pick up each module's extra as that module's tests are added, rather than installing all four modules' heavy dependencies (torch-geometric, transformers, rdkit, ESM-2) before any of them are used — that would make every CI run slow for no benefit until there's code to actually test.
- **Minimum Python raised from 3.10 to 3.12**: discovered by actually running `make check` rather than assuming it would pass. `numpy` 2.5's bundled type stubs use a PEP 695 `type` alias statement, which mypy only accepts when its configured target `python_version` is 3.12+; targeting 3.10 made mypy fail on numpy's own stub file, not on project code. Rather than pin numpy to an older release to keep supporting 3.10, raised `requires-python`, `ruff`/`black` target-version, mypy's `python_version`, and the CI Python version to 3.12 together, since the ML dependencies this project pulls in (torch, transformers, PyG) all support 3.12 anyway.

## 2026-07-19 — Module 1 scaffold

- **Branch**: `module/1-cellpainting`, per the branching convention in `CONTRIBUTING.md`.
- **Package layout**: module source lives at `modules/1_cellpainting/src/cellpainting/`, registered as its own top-level `cellpainting` package in `pyproject.toml`'s `[tool.hatch.build.targets.wheel]` and in `[tool.mypy] files`, rather than importing module code by relative path. This keeps the module independently importable and testable, consistent with `ARCHITECTURE.md`'s module-layout convention, without introducing a shared code layer beyond `common/`.
- **Data subset not yet chosen**: `configs/data.yaml` and the module README both scaffold the one-plate / 10-15-compound validation subset with the batch/plate/compound fields left explicitly empty rather than guessed, since picking them requires inspecting what's actually available in the JUMP-CP S3 bucket. Next concrete step is writing the download script and picking real values against it, not assuming a plate ID in advance.
- **Dockerfile written but not yet runnable end-to-end**: it installs the `cellpainting` extra and defaults to importing the package as a smoke check, with a comment pointing at the eventual training entrypoint, rather than pretending a training/eval CLI already exists.
- **CI**: switched the push-triggered workflow's install step from `.[dev]` to `.[dev,cellpainting]` now that this module has code for it to exercise, per the plan already noted in the "CI scope for now" entry above. Left the weekly smoke test on `.[dev]` only, since there's no fixture-based pipeline yet for it to run.
